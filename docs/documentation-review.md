# Qizhu 设计文档评审

> 历史报告：评审针对 2026-10-14 的文档版本，后续规范和实现已有更新。当前代码与未完成工作见[2026-10-15 反查清单](remaining-work.md)。正文保留供追溯。

评审日期：2026-10-14
评审对象：`README.md`、`docs/architecture.md`、`docs/development.md`、`docs/technology-stack.md`
评审范围：**只评审文档本身**，不评估功能是否已实现。关注文档之间的口径冲突、设计空缺、表述是否可执行、以及文档治理。

## 1. 总体结论

四篇文档的**选型覆盖面很好**，`technology-stack.md` 尤其完整（10 节、状态标注规范、有参考链接）。作为"技术选型基线"它是合格的。

但它还不是一套**可执行的设计文档集**，问题集中在三类：

| 问题类型 | 数量 | 严重度 |
| --- | --- | --- |
| A. 文档之间口径冲突 | 6 项 | 中 |
| B. 设计章节缺失 | 57 项，分布见第 3 节 | 高 |
| C. 表述模糊、无法判定 | 8 项 | 中 |
| D. 文档治理机制缺失 | 8 项 | 中高 |

一句话概括：**选型写清了"用什么"，但没写清"怎么定规矩"**——数据怎么建模、编码怎么命名、错误码怎么编、权限码长什么样、配置项有哪些、日志字段叫什么、提交怎么做，这些"通用规范"在所有四篇文档里都是空的。

## 2. A 类：文档之间的口径冲突

| 编号 | 冲突点 | 说法 A | 说法 B | 建议 |
| --- | --- | --- | --- | --- |
| A-1 | .NET SDK 版本要求 | README「需要 .NET 10 SDK」 | tech §9「global.json 指定 10.0.100，rollForward=latestFeature，禁止预览版」 | README 应说明版本**解析策略**与最低可用 SDK，否则新人可能装 10.0.1xx 之外的版本 |
| A-2 | 容器构建的完成度 | README「已初始化的能力」把"容器构建文件"列为已具备能力 | tech §8「Dockerfile 已配置；本机 Docker 服务未启动，**尚未验证镜像构建**」 | 两处口径需统一为"已配置未验证"，或明确 README 的"能力"一词是否包含未验证项 |
| A-3 | 前端在工程结构中的位次 | README「工程结构」表只有 5 个 .NET 项目 | tech §2 规定前端目录为 `web/` | README 结构表应补前端行（标注"待创建"），否则结构表与目标状态不一致 |
| A-4 | 开发环境 HTTP / HTTPS | README 给 `http://localhost:5080`；`launchSettings.json` 只有 http profile | tech §5「现有 Cookie 设置要求 HTTPS，接入正式登录时**本地开发也配置 HTTPS**」 | 文档需说明**何时切换**、开发证书如何生成与信任、切换后 dev.ps1 与 README 如何改 |
| A-5 | 就绪检查的定义 | README「当前边界」只提存活检查 | arch「运维边界」说"另加就绪检查" | 需明确就绪检查的**判定内容**（探哪些依赖）、失败时编排系统应如何处理 |
| A-6 | 全局授权与匿名标记的关系 | dev「新增接口默认受认证保护；只对确实公开的接口显式使用 `AllowAnonymous`」 | 未说明 `AllowAnonymous` 会**绕过** FallbackPolicy | 应补充警告：`AllowAnonymous` 一旦误用会静默开放接口，说明当前的防护手段是什么 |

## 4. C 类：表述模糊、无法判定

这些说法在文档里大量出现，缺少**触发条件**与**判定标准**，导致"什么时候该做"无法回答：

| 编号 | 表述 | 问题 |
| --- | --- | --- |
| C-1 | "建议采用""按需采用""后续建设""待接入" | 没有触发条件，也没有责任人，无法判断何时该启动 |
| C-2 | "模块可选择启用" | 启用方式是配置、编译期还是部署组合？未定义 |
| C-3 | "不在生产启动时自动修改表结构" | 那开发环境用 CodeFirst 还是 DbUp 脚本？两条路径并存，缺**唯一事实来源**的说明 |
| C-4 | "敏感配置通过环境变量或密钥服务注入" | 开发期用什么？生产选哪个？未定 |
| C-5 | "数据库是业务事实来源，Redis 不承担唯一存储" | 原则清晰，但缺缓存一致性的具体约定 |
| C-6 | "不承诺直接切换连接字符串即可兼容" | 合理，但缺"客户要求其他数据库"时的评估清单 |
| C-7 | "新增业务还需明确事务边界、并发策略、唯一约束和迁移流程" | 把决策推给实现者，文档自身未提供默认值 |
| C-8 | "编写有意义的测试" | 无法判定；缺"哪些类别必须覆盖"的清单 |

## 6. 建议补齐的文档集

评审建议把文档体系分层，而不是继续往现有四篇里塞内容：

| 层次 | 文档 | 优先级 |
| --- | --- | --- |
| 索引与共识 | `docs/index.md`（文档地图与阅读顺序）、`docs/glossary.md`（术语表） | P0 |
| 决策类（不定就返工） | 数据模型与类型规范、错误码字典、权限码规范、多租户 Identity 模型、租户生命周期 | P0 |
| 规范类（并行开工前提） | API 契约、开发规范补充（Git / 评审 / 版本）、配置项与环境矩阵、安全基线 | P1 |
| 治理类 | ADR 目录、未决问题清单、版本与变更记录、CONTRIBUTING | P2 |
| 交付类 | 可观测性规范、发布与回滚、前端工程规范、测试策略 | P2 |
| 远期 | 容量与性能基线、国际化设计、第三方身份设计、公共模块升级机制 | P3 |

## 7. 建议的处理顺序

1. **先补 P0 决策类**（数据模型与类型规范、错误码字典、权限码规范、多租户 Identity 模型）——这些是其他文档的输入，先定它们才不会有返工。
2. **再补索引与治理**（文档地图、术语表、未决问题清单、ADR 目录）——成本低，但能立刻解决 D-1~D-5。
3. **然后补规范类**（API 契约、Git / 评审 / 版本、配置与环境矩阵、安全基线）——这是前后端能并行开工的前提。
4. **最后清理既有四篇**：消除第 2 节的 6 项口径冲突，把第 4 节的模糊表述替换为可判定标准，把时点快照移出基线文档。
